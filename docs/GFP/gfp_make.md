# gfp_make

gfp_make is the primary means by which structures are converted into fingerprint form.

A typical usage might be
```
gfp_make file1.smi > file1.gfp
gfp_make file2.smi > file2.gfp
gfp_tool* file1.gfp file2.gfp > result
```
where the result is some kind of comparison between the molecules in 'file1' and 'file2'.

## Details
gfp_make is a fundamentally simple too, that converts a set of fingerprint specifications
given on the command line to a (possibly pipelined) invocation of one or more
tools that add fingerprints to an input stream.

For example if you invode with the default arguments, and add the -v (verbose) option,
it will show what commands are executed. That might look like
```
temperature -J MPR -E autocreate -g all -l file.smi |
        maccskeys -E autocreate -n -J FPMK -J LEVEL2=FPMK2 -f - |
        iwfp -E autocreate -J FPIW -f -
```
where the default fingerprint, -MPR -IW -MK -MK2, have been turned into three
program invocations. The tool [temperature](/docs/Molecule_Tools/temperature.md)
initiates processing, standardising the smiles, stripping to the largest
fragment, and then writing the fingerprint, with molecular properties, to the output.
The next stage of the pipeline is an invocation of [maccskeys](/docs/Molecule_Tools/maccskeys.md)
which is instructed to generate two fingerprints, the normal, and the level 2 fingerprint
which accounts for number of times set. The resulting stream is then passed to
[iwfp](/docs/Molecule_Tools/iwfp) which adds the linear fingerprint to the
stream. gfp_make is responsible for constructing these command pipelines, which
can be of arbitrary complexity.

### Implementation
The current gfp_make is a perl script, that was first initiated in the 1990's and
has been in continuous use ever since. It has grown considerably and is now too
complex. Work is underway on a ruby alternative that promises to be more
flexible and maintainable. The design has however proven to be remarkably
adaptable and useful, with gfp_make now also serving as the core of svmfp models.

Is invoked with no arguments, gfp_make.sh reports the following options available.
```bash
gfp_make.sh
Generates composite fingerprints, smiles > stdout
 -STD           shortcut for -MK -MK2 -IW -MPR
 -MK            FP MACCS keys
 -MK2           FP MACCS keys level 2 - multiple feature determination
 -MPR           FP molecular properties (natoms, nrings, ...)
 -IW            FP IW fingerprints
 -EC<r>:<T>     FP Extended Connectivity fingerprints, radius <r> type <T> (ZYHAPCR)
 -MAP           FP Merck Atom Pairs (custom atom types)
 -MAP<r>:<T><n> FP Merck Atom Pairs radius <r> type <T> (ZYHAPCR), iter <n>
 -SCF0          FP fingerprint of the molecular scaffold, -SCFI to differentiate substitution patterns
 -W <dname>     include fingerprint of descriptor <dname>
 -expert        more options
 -v             verbose output
```
This is a small subset of the fingerprints that can be generated by `gfp_make.sh`. See
more by using the `-expert` option.

To get the default, or standard, set of fingerprints
```
gfp_make.sh file.smi > file.gfp
gfp_make.sh -STD file.smi > file.gfp
gfp_make.sh -MPR -IW -MK -MK2 file.smi > file.gfp
```
should all yield the same result.

This default, or standard, set of fingerprints has been tuned for concordance with
human perceptions of chemical similarity. The -IW fingerprint is a linear path
fingerprint, similar to the Daylight linear fingerprint. Paths up to length 7
are computed. The default atom type is atomic number, but that can be changed if
needed, `gfp_make.sh -w -P UST:AHY -w file.smi > file.gfp

## Fingerprints
Numerous tools within LillyMol have been
implemented so they are compatible with the expectations of gfp_make.

Primarily this involves two functionalities.

1. Read a molecule and generate a fingerprint.
2. Read an already formed fingerprint stream froms stdin and insert one or more extra fingerprints.

We see that in the above example, where the pipeline is shown, temperature is satisfying the first requirement,
while maccskeys and iwfp the second. The order in which various tools are added
to the pipeline is hard coded within the logic of gfp_make, and is not meaningful.
This is an important property because it means that fingerprint files generated with
the same fingerprints will always have the same ordering and so can readily be
compared.

`gfp_make.sh` can read either a smiles or existing TDT (GFP) file from stdin
```
generate smiles | gfp_make.sh -ECC3 - > products.gfp
```
Or to consume a fingerprint
```
generate fingerprint | gfp_make.sh -ECC3 -tdt - > products.gfp
```
Note that this may (silently) generate duplicate fingerprints if the '-ECC3' fingerprint
is already in the fingerprint when it arrives at gfp_make.sh. Nothing prevents that.
Use `tdt_stats` to get an understanding of what tags are in a .gfp file. Similar
problems occur if a fingerprint is specified multiple times to gfp_make.sh
```
gfp_make.sh -AP10:AHY -AP10:AHY -RS file.smi > file.gfp
```
will result in duplicate AP10 fingerpronts in `file.gfp`. This will likely
fail when any gfp tool attempts to use that fingerprint file.

### Connection table errors.
It is possible to have gfp_make.sh skip invalid smiles, but care is needed. If the `-icte` option
is passed, the first pipeline component is given the `-i ICTE` option. There is a chance that
this might generate useful results if generating fingerprints from a smiles file,
but if reading from an existing fingerprint file, this is much more likely to result
in erroneous, or fatal outcomes. All LillyMol input qualifiers are available for use via the
`-i` option. Just as for the command line tools, specify any number of `-i` flags.
These flags will be passed to the first LillyMol executable in the pipeline.
